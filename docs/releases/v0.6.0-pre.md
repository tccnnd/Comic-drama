# Release v0.6.0-pre — shot-level-video-rendering

Date: 2026-07-12 (pre-release; implementation 15/17 tasks complete)
Spec: `.kiro/specs/shot-level-video-rendering/`

## Summary

Extends the video generation mainline from scene-level to shot-level
rendering. When `VIDEO_RENDER_GRANULARITY=shot` is active, each
`shot_plan.shots[]` item is rendered through the video provider individually,
assembled into a scene clip via ffmpeg hard-cut concat, and per-shot
provenance is persisted in version-2 `generation_meta`. Scene-level rendering
remains the default; shot-level is opt-in.

Acceptance chain:

```text
shot_plan.shots[]
  → per-shot provider request inputs (prompt, camera, visual_content, continuity)
  → quota validation (calls, seconds, cache reuse)
  → render_shot_with_provider_policy (retry + fallback per shot)
  → assemble_shot_clips (ffmpeg concat + assembly manifest)
  → version-2 generation_meta + canonical timeline shot_timeline[].generation
```

## Highlights

- **Render granularity resolution** (`video_render_granularity`): precedence is
  CLI flag → API/runtime request → safe project setting → environment default
  → built-in `scene`. The `shot` mode is parsed and persisted but does not
  alter the default scene-level path.
- **Quota dry-run** (`estimate_shot_render_quota`,
  `validate_shot_render_quota`): estimates shot count, provider calls, and
  generated seconds before live submission. Raises `VideoShotQuotaError` when
  `VIDEO_SHOT_MAX_CALLS` or `VIDEO_SHOT_MAX_SECONDS` would be exceeded. Cache
  reuse is accounted for when `VIDEO_SHOT_REUSE_CACHE=1`.
- **Per-shot provider request inputs** (`build_shot_provider_request_inputs`):
  carries per-shot prompt, negative prompt, timing, `temporal_spec`,
  `consistency_spec`, camera payload, intent payload, visual content,
  continuity hints, and resolved provider/model metadata. Video model
  resolution explicitly avoids `LLM_MODEL` planning-model leakage.
- **Shot render with provider policy** (`render_shot_with_provider_policy`):
  reuses the existing retry/backoff and `report`/`strict`/`silent` fallback
  modes at the shot level. Returns sanitized `shot_outputs[]` metadata.
- **Shot clip assembly** (`assemble_shot_clips`): filters usable
  real/fallback/skipped shot outputs, assembles them with ffmpeg concat hard
  cuts, and writes a stable `shot_assembly_manifest.json`. Failed shot outputs
  are excluded from assembly but remain visible in provenance.
- **Scene-level shot orchestration**
  (`render_scene_shots_with_provider_policy`): iterates ordered
  `shot_plan.shots[]`, validates quota, renders/reuses each shot, assembles
  the scene clip, and persists version-2 aggregate `generation_meta`.
- **Fallback modes at shot level**:
  - `report`: renders local fallback clips for failed shots, assembles mixed
    real/fallback scene clips, records per-shot warnings.
  - `strict`: raises before publishing an assembled scene clip or persisted
    metadata; no video asset is produced.
  - `silent`: records fallback shot outputs and aggregate metadata while
    suppressing warning text.
- **Resume and targeted rerender** (`build_shot_cache_key`,
  `rerender_scene_shot_video`): deterministic cache keys enable reuse of
  unchanged successful shot outputs. `force_shot_id` supports targeted rerender
  of a single shot; unchanged shots are reused and the scene clip is
  reassembled. Backend endpoint:
  `POST /api/projects/{project_id}/scenes/{scene_order}/shots/{shot_id}/rerender-video`.
- **Canonical timeline and snapshots**: `build_canonical_timeline` enriches
  `shot_timeline[]` items with compact per-shot `generation` copied from
  `generation_meta.shot_outputs[]`. `project_snapshot` exposes compact
  `shot_render_status` in `scene_graph.scenes[]` while keeping full
  `generation_meta` on each scene. Legacy scene-level projects fall back to
  planned shot rows without requiring shot render metadata.
- **Review Console integration**: read-only shot render summaries and per-shot
  rows from `generation_meta.shot_outputs[]` or canonical
  `shot_timeline[].generation`. Targeted `Rerender shot` controls for
  `video_render_granularity=shot` scenes with concrete `shot_id`s.

## Configuration

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `VIDEO_RENDER_GRANULARITY` | `scene` | `scene` or `shot`. |
| `VIDEO_SHOT_MAX_CALLS` | `8` for remote providers; unlimited for local/ComfyUI | Max provider calls per scene. Set `0` to disable. |
| `VIDEO_SHOT_MAX_SECONDS` | `40` for remote providers; unlimited for local/ComfyUI | Max generated seconds per scene. Set `0` to disable. |
| `VIDEO_SHOT_DRY_RUN` | (unset = false) | When truthy, estimate quota without submitting. |
| `VIDEO_SHOT_REUSE_CACHE` | (unset = false) | When truthy, reuse unchanged successful shot outputs. |

Override order: CLI flag → API/runtime request → safe project setting →
environment default → built-in default.

- `python -m pytest -q tests\test_video_provider_mainline.py` — 41 tests
  covering shot plan, generation meta v1/v2, shot output sanitization, quota
  validation, provider request inputs, shot render with policy, assembly,
  scene-level orchestration, fallback modes, targeted rerender, canonical
  timeline, and legacy project normalization.
- Mock-provider integration tests (task 15) cover the five acceptance
  scenarios: all-real two-shot scene, mixed report fallback, strict failure,
  targeted rerender reuses unchanged shots, and quota dry-run blocks before
  submit.

## Known Limitations

- **Live validation EVALUATED (task 17, 2026-09-01)**: controlled two-shot
  XL submit reached the aggregator (`ready=True`) but returned HTTP 429 on
  all 6 attempts (quota/rate-limit). `report` fallback assembled a valid
  10.00s 1080x1920 h264 scene clip; `shot_outputs` persisted with
  `status=fallback`, `provider_id=xl`, and the 429 error. Evidence:
  `outputs/gate_c_shot_xl_20260901_220421/live_validation_result.json`.
  Shot-level XL `real_video` success remains unproven until 429 clears.
- **Hard-cut concat only**: the current assembler uses ffmpeg hard cuts.
  Transition polish (cross-fade, motion interpolation) is a future follow-up.
- **Scene-level remains default**: existing projects and workflows are
  unaffected unless `VIDEO_RENDER_GRANULARITY=shot` is explicitly set.
