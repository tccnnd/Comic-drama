# Provider Viability Rubric

> **目的**：给 video provider 选型一个**可重复、可对比**的尺子。  
> **配套**：`docs/provider_research.md`（候选对比表）。  
> **自动化**：`scripts/provider_viability_gate.py`（待实现；阻塞：前端 ESM 阻断修复 + scorecard 接入）。  
> **版本**：v0.2.0 video-provider-mainline 准备阶段。

## 1. 评分原则

- **6 维度 × 0–5 分** = 总分 30 分
- **0–1 分 = 弱项**（不直接 fail，但总分会被显著拉低）
- **任意 fail 规则触发 = 直接出局**，不进入总分计算
- **理论分 vs 实测分**：桌面研究只能给理论分（基于公开信息）；实测后用 `scripts/provider_viability_gate.py` 跑出实测分
- **维度分必须整数**：0、1、2、3、4、5（不接受 2.5、3+ 等）

## 2. 六维度 0–5 分定义

> 每维度的 0/3/5 是关键锚点；1/2/4 是中间过渡。

### 2.1 API 稳定性

| 分 | 描述 |
|---|---|
| 0 | API 不可用 / 文档为零 / 完全没有 SDK / 已停止维护 |
| 1 | API 可用但 5xx 频繁、无重试机制、QPS 限制 < 1 |
| 2 | 偶发 5xx，需手动重试 + 降级；QPS 1–5 |
| 3 | 稳定但偶有慢响应；平均 RT 10–30s；QPS 5–10 |
| 4 | 稳定 + 平均 RT < 10s + 监控告警 + 配额预警 |
| 5 | SLA ≥ 99% + 自动重试 + 配额预警 + 完整 SDK + Cookbook + 沙箱环境 |

### 2.2 文档质量

| 分 | 描述 |
|---|---|
| 0 | 无文档 / 文档已 2 年未更新 / 链接 404 |
| 1 | README + 接口列表，无错误码说明 |
| 2 | API 文档完整（参数/响应/错误码）|
| 3 | API 完整 + 多语言 SDK 示例 + 错误码表 |
| 4 | API 完整 + Cookbook + 错误码表 + 限流说明 |
| 5 | Cookbook + 案例库 + 社区活跃 + 最佳实践 + 视频教程 |

### 2.3 国内可访问性

| 分 | 描述 |
|---|---|
| 0 | 完全不可访问 / 已下架中国大陆 / 触发 fail F3 |
| 1 | 需要特殊网络工具（高合规风险）|
| 2 | 偶尔可用 / 需海外代理 / 平均 RT > 10s |
| 3 | 稳定但慢（平均 RT 5–10s）|
| 4 | 稳定（平均 RT < 2s）|
| 5 | 多区域 CDN + 稳定（RT < 1s）+ 合规备案 + 国内 SLA |

### 2.4 成本（按 4s / 1080p 标准镜头）

| 分 | 描述 |
|---|---|
| 0 | > 5 元/秒（不可承受）→ 触发 fail F4 |
| 1 | 3–5 元/秒（高）|
| 2 | 1–3 元/秒（中）|
| 3 | 0.5–1 元/秒（合理）|
| 4 | ≤ 0.5 元/秒，或阶梯价 + bulk 优惠 |
| 5 | ≤ 0.3 元/秒，或免费额度 + bulk + 阶梯优惠 |

### 2.5 输出质量（5 镜头实测）

> **5 个镜头** 来自 `inputs/viability_test/`，覆盖：人物特写、对话、空镜、运动、复杂场景。  
> 镜头由 v0.5.0 `director_plan` 自动生成。

| 分 | 描述 |
|---|---|
| 0 | 5 镜全废（无法使用）→ 触发 fail F2 |
| 1 | ≤ 1 镜可用（基本不可用）|
| 2 | 2 镜可用 |
| 3 | ≥ 3 镜可用（基本可用）|
| 4 | ≥ 4 镜可用 + 人物基本稳定 |
| 5 | 5 镜全可用 + 人物稳定 + 运动流畅 + 风格一致 |

### 2.6 漫画/短剧适配

| 分 | 描述 |
|---|---|
| 0 | 风格完全错（动漫 prompt → 写实结果，且无法通过 prompt 修正）|
| 1 | 风格错但可勉强用，需大量人工后期 |
| 2 | 风格凑合，线条/色彩偏差大 |
| 3 | 风格基本对，但人物稳定性差 |
| 4 | 风格对 + 人物稳 + 首尾帧可控 |
| 5 | 风格对 + 人物稳 + 首尾帧控 + 镜头语言丰富 + 多角色一致 |

## 3. 直接 fail 规则（任意一条即出局）

> 这些规则是**硬约束**，不进入总分计算。一旦触发直接 fail。

| 规则 ID | 触发条件 | 检测方式 |
|---|---|---|
| **F1** | API 不可用 | 文档/SDK 为零 + 注册流程不通 + 健康检查 5 次全失败 |
| **F2** | 实测全废 | 5 个测试镜头全部不可用（VLM 评分均 < 0.3）|
| **F3** | 完全无法访问 | 国内 + 海外代理 + 移动网络 三路全不可达 |
| **F4** | 价格不可承受 | 单价 > 5 元/秒 且无 bulk 优惠 |
| **F5** | 版权风险 | 商用条款不清晰 / 训练数据来源不明 / 输出版权不归用户 |
| **F6** | 已被监管下架 | 在中国大陆已下架或合规风险高 |

## 4. 自动化 vs 人工

### 4.1 自动化（4 维度，可写脚本）

| 维度 | 自动化方式 | 输出 |
|---|---|---|
| API 稳定性 | 健康检查脚本（提交 + 轮询 + 测 RT）| RT 中位数 / P95 / 失败率 |
| 国内可访问 | 多地 ping + curl（5 节点：北京/上海/广州/成都/香港）| 各节点成功率 + 平均 RT |
| 成本 | 按 API 调用自动统计 + 阶梯计费 | 实际单价（实测 5 镜头后）|
| 输出质量 | VLM 评分（CLIP-IQA）+ 人工抽检 20% | 5 镜可用数 + 风格一致性分 |

### 4.2 人工（2 维度，必须人评）

| 维度 | 人工方式 | 评审计时 |
|---|---|---|
| 文档质量 | 看完整 Cookbook + 案例库 + 错误码表 | 30 分钟/provider |
| 漫画适配 | 5 镜头集中对比 + 主观打分 | 1 小时/provider |

## 5. 评分流程

```text
1. 准备 5 镜头 reference（inputs/viability_test/）
       │
       ↓
2. 注册账号 + 申请 API key（写入 .env，不入 git）
       │
       ↓
3. 跑 scripts/provider_viability_gate.py
       - 自动跑 4 维度（API/国内/成本/质量）
       - 输出 JSON 报告 → outputs/viability/<provider>_<date>.json
       │
       ↓
4. 人工跑 2 维度（文档质量、漫画适配）
       │
       ↓
5. 汇总总分 + 触发 fail 检查
       │
       ↓
6. 填表 → 更新 provider_research.md 理论分为实测分
```

## 7. 决策矩阵

| 总分区间 | 建议 |
|---|---|
| 25–30 | **主推** |
| 20–24 | **备选** |
| 15–19 | 仅作 fallback |
| < 15 | 淘汰 |
| 触发任何 fail | 直接淘汰（无论总分）|

## 8. 与代码的对齐

| Rubric 维度 | 代码侧对应 |
|---|---|
| API 稳定性 | `scripts/video_provider_adapters.py` 中的 `*_poll` / `*_submit` 函数 |
| 国内可访问 | `video_providers.py` 中 `backend="remote"` 时的 BASE_URL 域名 |
| 成本 | `.env` 中的 `*_API_KEY` + 阶梯计费说明 |
| 输出质量 | `outputs/<run_id>/scene_*/video.mp4` + scorecard |

实测后新增 provider 需在 `video_providers.py` 加 `register_video_provider(VideoProviderSpec(...))`，并在 `scripts/video_provider_adapters.py` 加对应 adapter 函数。

## 附录 A — 评分一致性建议

- **同分争议**：如果两位评测人对同一 provider 的某一维度分歧 > 1 分，取**低分**（保守原则）
- **跨 session 一致性**：每次实测时记录评测人 + 日期，便于横向对比
- **价格变动**：成本维度每季度复核一次（价格波动大）

## 附录 B — 与 Phase 1 的关系

Phase 1 "Real Video Generation" 的目标是把生成的 video clip 作为 first-class scene media。本 rubric 的输出直接决定 v0.2.0 video-provider-mainline 的主推 provider。一旦主推确定，需在 `video_providers.py` 把对应 provider 设为默认，并更新 `docs/self_hosted_video_provider.md` 的配置示例。
